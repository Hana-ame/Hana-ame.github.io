AtlasCanvas 不是下一个白板应用，而是一套面向 B 端大场景的可编程画布引擎底座

基于对项目全部 23,959 行 TypeScript 源码与 51 项单元测试的深度代码审计（评估时间：2026 年 11 月），对照 Miro、Excalidraw、ComfyUI、React Flow 与 tldraw SDK 剖析其架构亮点、工程短板与三条现实商用路径。

B2B / SDK
最佳商用定位 · 不建议直面 C 端白板红海
核心结论：AtlasCanvas 在空间分区调度（512×512 Chunk + 离屏瓦片 LRU）、画布内后端驱动交互与生产级脚本/代理安全沙箱上远超一般原型项目，极具工程可取之处；但它目前缺乏富媒体编辑、强类型 DAG 数据流端口与多人 CRDT 协同，不能直接作为 C 端创作工具变现，而最适合切入垂直行业超大场景空间控制台或私有化无限画布 SDK。

与现有创作蓝图工具相比，它卡在“游戏地图调度”与“应用蓝图”的交叉缝隙

市面上的“创作蓝图与无限画布工具”实际上分化为三大阵营：面向终端用户的协作白板与视觉笔记（如 Miro、Excalidraw、Heptabase 与 Milanote）、面向生成式管线的AI 节点工作流（如 ComfyUI、Freepik Spaces），以及面向研发团队的底层画布引擎 SDK（如 tldraw SDK、React Flow / xyflow）。AtlasCanvas 的真正对标对象不是 Miro，而是第三类底层引擎，并在空间分区加载与内置安全执行层上做出了明显差异化。

四个最值得保留的架构设计亮点

与市面上常见的“套壳白板 Demo”不同，AtlasCanvas 的代码库在底层调度、交互范式与安全防御上展现出极高的一致性与工程克制。

1. 地图级的空间哈希 Chunk 调度

核心引擎（chunkManager.ts 与 chunkTileCache.ts）将无限画布切分为 512×512 离散分区，原生支持正负坐标映射、跨分区实体追踪、视锥剔除与 128 块离屏瓦片 LRU 缓存。平移数千实体时仅需执行可见分区级别的 drawImage 拷贝；当缩放低于 0.35× 全景时自动抑制边缘流式拉取，避免请求风暴。还独创了类似 Excel 的行列标尺与最多 400 格的多区选块（chunkSelection.ts）及 URL Hash 精确跃迁（/#chunk=4,-2&zoom=1.25）。

2. “所见即操作”的世界空间控件

渲染内核完全不依赖 React DOM 叠层，而是采用 Immediate-Mode Canvas 2D 绘制所有控件、按钮与系统工作台，并在每帧注册世界坐标 AABB 热区（worldControls）。含交互按钮的控件会自动脱离静态瓦片进入实时交互层，确保在漫游模式下“看到就能点”。同时实现了视觉等大字号换算（worldFontSize ← base / zoom）与宏观视图标题保留算法，解决了传统无限画布“缩远就看不清字”的痛点。

3. 后端驱动的控件与双维度变量存储

控件（RectEntity）支持纯后端 JSON 下发按钮排版、9 类声明式动作与多步 sequence 流水线。更具巧思的是 SpatialVariableStore：动作产生的运行时变量既挂载于单个实体（entity.vars），也按整数分区坐标 (cx, cy) 聚合索引，并支持 {{chunk(cx,cy).vars.*}} 跨区模板插值——相当于在画布上内置了一个“空间共享黑板”。

4. 罕见的生产级安全沙箱与 SSRF 防护

这是该项目最令人意外的加分项：用户自定义按钮脚本并非在主线程直接 eval，而是经过静态安全审计后运行于隔离的临时 Web Worker（零 DOM/Cookie/Storage 权限、5 秒 CPU 超时强杀）；导入外部 JSON 时默认锁定脚本并弹出 ScriptTrustModal 逐条审计；服务端 server.ts 的 /api/proxy 具备 DNS 重绑定校验、内网与云元数据 IP（169.254.169.254）拦截、禁止 3xx 跳转与密钥白名单注入，大幅降低了企业安全验收阻力。

距离真正可交付的“创作蓝图产品”，还缺四块关键拼图

代码审计同样暴露了它作为“早期引擎原型”的清晰边界：在底层调度和安全护城河之外，面向终端创作者与生产级协同的核心能力目前仍处于缺位或单体耦合状态。

缺富媒体与 DAG 端口

当前实体仅限矩形、文本、锚点、折线、普通连线与面板 6 种。连线（ConnectorEntity）只是视觉关系线，没有输入/输出类型端口（Port）与上游触发下游的拓扑调度，也不支持图片/视频/音频/Markdown 预览节点，无法直接替代 ComfyUI 或 Milanote。

缺多人协同与真实后端

同步层（compatLayer.ts）定义了清晰的 5 个 REST 接口，但仓库内仅实现了基于 localStorage 和 BroadcastChannel 的本地 Mock 后端；缺乏 CRDT（如 Yjs）并发冲突合并、在线协作光标以及带空间索引（PostGIS / R-Tree）的真实服务端持久化。

核心单体过重（5,061 行）

engine.ts 达 5,061 行、canvas2DRenderer.ts 超过 100 KB，交互状态机、工具逻辑与业务分支高度集中。纯 Canvas 2D 自绘在复杂中文输入法（IME）、跨块文本选区复制与无障碍阅读（A11y）上的长期维护成本也会显著高于混合渲染架构。

商用潜力评估：底层底座已过及格线，但变现必须绕开 C 端通用白板

综合代码质量、安全底座与市场竞争格局，AtlasCanvas 具备明确的商用可行性，前提是放弃“做给个人创作者用的免费白板”这一红海幻想，转而将其“纯 TS 零框架依赖 + 超大空间分区 + 后端驱动安全交互”的技术长板卖给对性能、可控性和内网部署有硬性要求的 B 端客户或开发者。

商用路径 目标客户与核心场景 变现模式参考 必补工程项 推荐优先级
路径 A：垂直行业大场景空间操作台 游戏世界观/关卡策划大地图、工业数字孪生/物联网拓扑台、大型微服务运维编排台 B2B 私有化授权 + 行业定制交付（客单价高、对 C 端颜值要求低于性能与内网安全） PostgreSQL 空间索引后端、RBAC 权限与审计日志、领域专用实体模板 高（最快变现）
路径 B：自主可控无限画布 SDK 需要嵌入无限画布但难以承受 tldraw $6,000/年 授权或受限于 DOM 性能的研发团队 Open-Core（核心 MIT 开源 + 企业级 Chunk 后端/协同/商业支持订阅，参考 React Flow Pro） 拆分 engine.ts 单体、发布标准 npm 包、完善英文/中文 API 文档与插件钩子 中高（中长期壁垒）
路径 C：嵌入式 AI Agent 蓝图工作台 企业内部 AI 编排平台、垂类 AIGC 工具商（复用现有安全代理与动作链） 按席位 SaaS 或 OEM 组件授权（避免与 ComfyUI 拼通用算子数量） 强类型输入/输出端口、异步流式输出渲染块、图片/音视频多媒体节点 中（需补 DAG 能力）
与其把 AtlasCanvas 包装成“又一个画画和贴便利贴的创作工具”，不如把它定位为“能直接调度后端接口的二维空间操作系统”——这才是现有白板和节点工具都没有彻底做透的生态位。

若计划推进商用，建议按三步走验证

  • 先重构解耦再对外开放（2–4 周）：将 5,061 行的 engine.ts 按“相机与视口 / 交互状态机 / 动作执行器 / 同步桥接”拆分为独立模块，把 5 个 REST 接口配齐一套基于 PostgreSQL + PostGIS（或 SQLite R-Tree）的最小参考后端，让外部团队 10 分钟就能跑通真实持久化。
  • 补齐最小创作闭环（4–6 周）：如果瞄准创作蓝图或 AI 工作流场景，优先增加图片/媒体节点与带类型校验的端口连线（Port-to-Port），把现有“点击按钮改变量”升级为“上游节点输出自动驱动下游节点”。
  • 选定单一垂直标杆场景验证付费：切忌在没有付费客户前盲目堆砌多人 CRDT 或上百种白板图形；先用“10,000+ 节点流畅漫游 + 节点内安全调用内部 API”这一不可替代优势，切入一个具体的游戏策划、运维拓扑或企业 AI 控制台客户做 PoC 签约。
